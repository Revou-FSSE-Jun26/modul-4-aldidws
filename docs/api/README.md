# API contract notes

This file lists the endpoints that were added or changed for the Kanban UI. The full route table is in `specs/design.md` section 5.2 (with the changes in 5.2.1), and the live Swagger UI is served by Flask at `/apidocs/`.

`frontend-request-payloads.json` in this folder holds one sample body for every request the frontend sends. Two tests read it so the frontend and the Marshmallow schemas cannot drift apart: `backend/tests/contract/test_frontend_payloads.py` and `frontend/lib/services/__tests__/contract.test.ts`.

## Conventions

- Auth: `Authorization: Bearer <access_token>` on every route below. A missing or invalid token returns 401 `UNAUTHORIZED`.
- Success: `{"data": ...}`; lists may add `meta`. Errors: `{"error": {"code", "message", "details"}}`.
- Resources on a board the caller does not own return 404 (existence is not disclosed).
- Field names are snake_case as serialized today (V-020 records the gap to `api-contracts.md`).

`due_date` is on every card object (board read, create, update, move, `GET /api/v1/cards`). It is `null` or a UTC string such as `2026-12-01T17:00:00Z` (second precision; offsets in the request are converted to UTC and fractions of a second are dropped). Moving a card does not change it. The column is added by migration `421f6e5e8ae5` (nullable, additive).

`priority` is on every card object (board read, create, update, move, `GET /api/v1/cards`). It is `null` or one of `"low"`, `"medium"`, `"high"`. Sort order: null sorts last. The column is added by migration `b3p0r10r1ty` (nullable, `VARCHAR(16)`, check constraint `ck_cards_priority`).

`labels[]` is on every card object (board read, create, update, move, `GET /api/v1/cards`). It is an array of `{id, name, color}` objects, sorted by name (case-insensitive), then name, then id. The arrays are populated by migration `43535c2f36bf` (additive).

### Column color and done flag

`POST /api/boards/{board_id}/columns` and `PATCH /api/columns/{column_id}` accept two optional fields:

- `color`: one of `gray`, `blue`, `orange`, `green`, `red`, or `null`. On PATCH, omitted = unchanged and `null` = reset (the client then cycles a color by column position). On POST, omitted = `null`.
- `is_done`: boolean. Omitted = unchanged (`false` on create). Strings and numbers are rejected.

Any other value returns 400 `VALIDATION_ERROR` with `details.color` or `details.is_done`. Ownership checks are unchanged.

Every column object (create, update, reorder response, and `columns[]` in the board read) now includes `color` (`null` or one of the five values) and `is_done` (boolean). The fields are added by migration `a2c0l0r5d0n1` (`color` nullable with check constraint `ck_board_columns_color`, `is_done` NOT NULL default false; additive).

### Priority field on cards

`priority` is present on every card object returned by the API (board read, create, update, move, label assignment, `GET /api/v1/cards`). It is `null` or one of `"low"`, `"medium"`, `"high"`. Sort order: null sorts last. The column is added by migration `b3p0r10r1ty` (nullable, `VARCHAR(16)`, check constraint `ck_cards_priority`).

- **POST** (create): omitting `priority` → `null`; sending `null` explicitly → `null`; sending `"low"`, `"medium"`, or `"high"` → stored as given.
- **PATCH** (update): omitting `priority` → unchanged; sending `"low"`, `"medium"`, or `"high"` → updated; sending `null` → cleared to `null`.
- Any other value returns `400 VALIDATION_ERROR` with `details.priority`.

### Create card position (`POST /api/v1/columns/{column_id}/cards`)

Optional body field `position`: `"top"` or `"bottom"`. Omitted = `"bottom"` (unchanged behavior: the card is appended after the last live card). `"top"` places the card first in the column in the same request and transaction. Soft-deleted cards are ignored when computing the position.

`cards.order` cannot be negative (`ck_cards_order_nonneg`). With `"top"`, if the first live card has `order >= 1` the new card gets `order - 1`; otherwise the live cards of the column are shifted down by 1 and the new card takes the old first order. The response contains the new card only, so clients must shift the other cards of the column locally when `order` of an existing card is less than or equal to the returned `order`.

Any other value returns 400 `VALIDATION_ERROR` with `details.position`. Ownership checks are unchanged (404 for a column of another user, 401 without a token). No migration.

### Labels (routes 27 to 31)

All five routes need a Bearer token (401 `UNAUTHORIZED` otherwise), reject unknown body keys with 400 `VALIDATION_ERROR`, and are scoped to boards the caller owns. Another user's board, label or card gives the same 404 as an unknown id. A path id that is not a UUID gives 404. Tables and constraints come from migration `43535c2f36bf` (additive).

Route 31 checks every id before changing anything: an id that is unknown or belongs to another board gives 404 `LABEL_NOT_FOUND` and leaves the card's labels as they were.

Colours: `blue`, `sky`, `graphite`, `silver`, `red`, `orange`, `green`, `purple`.

Objects. A **label** is `{id, board_id, name, color, created_at, updated_at}`. Every card object (board read, create, update, move, route 31, `GET /api/v1/cards`) has `labels: [{id, name, color}]`, sorted by name (case-insensitive), then name, then id. The board read (`GET /api/boards/{board_id}`) also has `labels: [label]` with all labels of the board. Deleting a board removes its labels. A soft-deleted card keeps its label rows. There is no limit on labels per board yet (D21).

`author_name` is the author's `name`, or the part of the email before `@` when the name is empty.

## Known gaps

- Because `cards_bp` is registered under two prefixes, `GET /api/v1/columns` answers the same as `GET /api/v1/cards`. No client uses it (`specs/design.md` 5.3).
- An invalid UUID in the path of the older routes still returns 500 (task B11).
- `page` and `per_page` on `/api/notifications` are not validated; a non-integer falls back to the default.
- Comment edit and delete do not check board ownership, only authorship.
